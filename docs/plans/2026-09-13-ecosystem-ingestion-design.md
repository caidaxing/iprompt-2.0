# 生态提示词库接入设计（15 仓库 / 20,000+ 条）

> 输入：WorkBuddy 整理的《00-总览MOC》（15 个 GitHub 提示词项目选型地图）与《01-提示词类型体系》（十二大类型框架）。
> 目标：把外部提示词生态接入 iPrompt Studio，成为多模型提示词工作站的真实内容量。
> 本文档只做方案，不含实施。

## 0. 一个关键洞察：15 个仓库要"分流转仓"

不是所有仓库都进案例库。按内容本质路由到三个去处：

| 去处 | 仓库 | 理由 |
|---|---|---|
| **案例库**（本文重点） | 02(13.4k⭐) 03(10.3k⭐) 04(8.1k) 06(3.8k) 09(733) 10(595) 11(489) 15(60) 12(269) 14(49) | 提示词合集，逐条入库 |
| **Skills 模块** | 05 wuyoscar-GPT-Image2-Skill、08 ai-image-prompts-skill | 本身就是 Agent Skill 包，走已规划的 Skills 模块（2026-09-13-skills-module-design.md） |
| **不接**（工具/参考） | 07 PromptEnhancer、13 prompt-studio | 是工具不是内容；其方法论吸收进类型体系文档即可 |

## 1. 类型体系升级：十二大类型成为全站统一展示分类

《01-提示词类型体系》的 12 类（人像摄影/电商广告/海报插画/角色手办/UI社媒/编辑修复/风格迁移/室内设计/教育信息图/职场生产力/视频/趣味社交）**正好补上跨模型统一浏览的缺口**：

- 现状：每个模型一套 rawAliases→展示分类，跨模型无法对齐
- 方案：**12 大类型作为全站统一展示分类**；每个模型的 Category 表把该模型源数据的原始分类映射到 12 类（rawAliases 机制原样复用，只是映射目标统一了）
- gpt-image-2 现有 6 Tab 迁移到 12 类：14 个原始分类 → 12 类的映射表一次性定好，重跑导入即迁移（原始分类保留在 Case.category 不丢信息）
- 类型体系文档收进仓库 `docs/类型体系.md` 作为映射规范的权威依据

## 2. 数据规模与存储策略

| 项 | 决策 |
|---|---|
| 体量 | 20,000+ 条入 Case 表（SQLite 单表 + 现有索引无压力） |
| **图片** | 外部语料**不下载图片**，保留上游 GitHub raw 预览 URL（CaseImage 本就支持外链 + lazy loading）；只有 gpt-image-2 核心库保持本地化。避免数 GB 下载与版权放大 |
| 编号 | num = 模型内编号：上游有稳定编号用上游（如 06 的连续编号），没有的按入库顺序自动分配 |
| 去重 | 按（modelId + prompt 归一化哈希）去重，保留首个并合并来源署名——多仓库收录同一条提示词很常见 |
| 来源溯源 | Case 加 `sourceRepo` 字段（仓库 id），source 继续存作者署名；未来可做"按来源筛选" |

## 3. 接入管线（复用现有模式，新增"适配器层"）

```
GitHub 仓库（raw 文件）/ 本地 Obsidian 全量笔记
        ↓  逐仓库适配器（唯一的脏活）
scripts/ingest/<repo-id>.mjs   →  归一化为统一中间格式（同 cases-<model>.json 结构）
        ↓  合并 + 去重
data/cases-<model>.json        →  现有 import-cases.mjs 原样复用（幂等 upsert）
```

- 每个适配器 = 一份"格式侦察 + 解析规则 + 分类映射（源分类→12 类）"
- 幂等可重跑：上游更新后重跑适配器即可增量同步
- **先侦察再写适配器**：每个仓库的真实格式（README 表格/JSON/Markdown 画廊）各不相同，动手前先抓样本分析，工作量评估以侦察结果为准

## 5. 前置依赖与风险

| 项 | 说明 |
|---|---|
| **模型切换 UI（Phase B）** | 接入第二个模型后，导航/浏览必须能切模型——E0 一并做掉（注册表驱动，半天） |
| 上游格式漂移 | 仓库会更新；适配器幂等可重跑，属常态维护 |
| 版权与署名 | 逐条保留 source 作者署名 + sourceRepo；多数上游为 MIT，README 总署名；语料质量参差（调研已知），去重后仍可能需要人工精选标记 |
| 搜索体验 | 2 万条 LIKE 搜索无压力；浏览深度靠 12 类 + 分页；后续可加标签筛选 |
| 工作量 | E0 ≈ 1 天；E1 ≈ 1-2 天（含两仓库格式侦察）；后续每仓库 0.5-1 天，取决于格式复杂度 |
