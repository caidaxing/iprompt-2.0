## 1. 背景与目标

现行注册制为「邮箱 + 密码 → 待审核 → 超管通过」。存在两个问题:

1. **邮箱归属无验证**:任何人拿别人的邮箱即可注册,审核通过后账号即归注册者
2. **超管操作负担**:每个注册都要人工审核,不可持续

**邀请码机制的目标**:信任前移——超管签发带**平台签名**与**有效期**的邀请码,持码者注册即激活,无需人工审核。

**本轮新增的两条硬性要求(负责人明确)**:

1. **邀请码必须有有效期**:不存在永久码;过期的码注册直接失败
2. **邀请码必须可验证为平台签发**:码自带平台 HMAC 签名,输入后第一步先验签——伪造的、凭空编的码,在碰数据库之前就被判定为"非平台签发"并拒绝

**非目标(本轮不做)**:邮箱验证、SMTP 通道、手机号/微信注册、自助找回密码。

## 2. 邀请码格式与验证(本轮核心设计)

### 2.1 码的形态:平台签名码

```
完整码 = 前缀 - 载荷 - 签名        (展示与输入均以连字符分组)
示例:  IP - 7K2M9P4QXD - F83K2M9A
```

| 段 | 说明 |
|---|---|
| 前缀 | 超管可选(默认 `IP`),便于标识发放批次/对象,如 `ZS` |
| 载荷 | 10 位随机字符(32 个无易混淆字符集,去掉 0O1lI) |
| 签名 | `HMAC-SHA256(签名密钥, 前缀+载荷)` 截取 8 位同字符集 |

- 签名密钥:环境变量 `INVITE_SIGNING_SECRET`;未设置时由 `AUTH_JWT_SECRET` 派生(`HMAC("invite-v1", AUTH_JWT_SECRET)`),零新增配置负担
- **只有平台能产出能通过验签的码**——不知道密钥就无法伪造;8 位签名 ≈ 40bit,穷举不可行

### 2.2 注册时的两级验证(顺序固定)

```
用户输入 → 归一化(去空格/连字符、转大写)
  ① 验签:HMAC(前缀+载荷) 与签名段比对
     ├─ 不匹配 → 「邀请码无效或已失效」(平台从未签发,不查库)
  ② 查库:码存在且 status=active 且 未过期 且 usedCount<maxUses
     ├─ 任一失败 → 同上统一文案
  ③ 全部通过 → 原子核销 + 创建 active 账号
```

两级验证的意义:验签解决"**是不是平台发的**";查库解决"**还能不能用**"(次数/禁用/过期)。

### 2.3 输入容错

大小写不敏感;忽略输入中的空格与连字符差异(`ip 7k2m9p4qxd f83k2m9a` 也能通过)。

## 3. 角色与流程

```
超管:管理页生成邀请码(设前缀/有效期/可用次数/备注)→ 平台产出签名码 → 发给目标用户
用户:注册页填 邮箱 + 密码 + 邀请码 → 两级验证通过 → 账号直接激活 → 即刻登录
超管(可选):禁用/启用某张码;用户列表溯源每个账号用的哪张码
```

### 关键产品决策(默认方案,待拍板)

| # | 决策点 | 默认方案 |
|---|---|---|
| D1 | 持有效签名码注册,是否还需人工审核 | **不需要,注册即 active**(码即信任;超管保留事后拒绝权) |
| D2 | 有效期 | **必填**。生成时可选 7 / 30 / 90 / 365 天,默认 **30 天**;不存在永久码 |
| D3 | 单码可用次数 | 默认 **5 次**,生成时可改(1~100) |
| D4 | 码前缀 | 默认 `IP`,超管可自定义(1~4 位,字母数字) |
| D5 | 存量 pending 测试用户 | 直接清理(生产库无真实用户) |

## 4. 功能需求

### FR1 邀请码生成(超管)
- 管理页「邀请码」Tab:前缀(可选)/ 有效期(**必选**:7/30/90/365 天)/ 可用次数(默认 5)/ 备注(必填)
- 平台产出完整签名码,生成后即可一键复制
- 生成记录立即入列表

### FR2 注册校验(游客)
- 注册表单新增**邀请码**输入框(必填,提示"请输入平台发放的邀请码")
- 按 §2.2 两级验证;任何失败统一返回「邀请码无效或已失效,请联系管理员」
- 通过后创建 **active** 账号并关联所用码,直接引导登录(不再有"等待审核"页)

### FR3 原子核销(防并发超用)
- 条件更新:`... WHERE code=? AND status='active' AND usedCount<maxUses AND expiresAt>now`,影响行数=0 即无效
- 与建号同事务语义:核销失败不建号;建号失败(邮箱冲突)回退核销

### FR4 邀请码管理(超管)
- 列表:完整码、前缀/备注、状态(有效/已禁用/已过期/已用尽)、已用/上限、到期时间、创建时间
- 操作:一键复制、禁用/启用(禁用只挡新注册,不影响已注册账号)
- 不提供删除(保留审计痕迹)

### FR5 溯源
- User 记录所用邀请码;用户列表展示码的前缀与备注(如"ZS · 发给张三")

### FR6 超管豁免
- ADMIN_EMAIL 注册路径维持现状:不需要邀请码,自动 active+admin

## 5. 数据模型

```prisma
model InviteCode {
  id        String    @id @default(cuid())
  code      String    @unique    // 归一化完整串(前缀-载荷-签名),注册校验键
  prefix    String               // 展示用前缀
  payload   String               // 随机载荷(验签输入)
  createdBy String
  maxUses   Int       @default(5)
  usedCount Int       @default(0)
  expiresAt DateTime             // 必填,签发时即确定
  note      String
  status    String    @default("active")
  createdAt DateTime  @default(now())

  users User[] @relation("InviteCodeUsers")

  @@index([status])
}

model User {
  // …既有字段不变…
  inviteCodeId String?
  inviteCode   InviteCode? @relation("InviteCodeUsers", fields: [inviteCodeId], references: [id])
}
```

签名不落库(验签是纯计算,密钥在服务端);`payload` 落库用于重验与展示。

## 8. 安全考量

- **防伪造**:HMAC 签名,无密钥不可产出有效码;验签先行,伪造码不触库
- **防爆破**:8 位签名 ≈ 40bit + 既有注册 IP 限流(10 次/h),穷举不可行
- **防超发**:条件 UPDATE 原子核销
- **防枚举**:所有失败统一文案,不区分"码错/过期/用尽"
- **密钥管理**:`INVITE_SIGNING_SECRET` 缺省派生自 `AUTH_JWT_SECRET`(零新增配置);泄露时更换即全量旧码失效(可接受,重新发码即可)
- **审计**:码的 note + User.inviteCodeId,账号↔码双向可溯

## 11. 验收标准

- [ ] 伪造码/随机编的码:验签失败被拒,且不产生数据库查询压力之外的副作用
- [ ] 过期码注册被拒(有效期必填生效)
- [ ] 用尽/禁用码注册被拒;有效码注册 → active + 直接登录 + usedCount+1 + User 关联码
- [ ] ADMIN_EMAIL 注册仍免码且自动超管
- [ ] 超管可生成签名码(自定义前缀)、复制、禁用/启用、查看进度;禁用后新注册立即被拒
- [ ] 输入容错:大小写/空格/连字符差异可通过
- [ ] 单测/E2E 全绿;lint/build 通过;发版按运维手册(exclude data/.env + 尾部斜杠 + 重启)
